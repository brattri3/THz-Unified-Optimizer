# STYLE_MANIFEST — оформление отчётов и презентаций зоны P

> Единый манифест стиля для всего, что зона P показывает владельцу. Держится в git и
> переиспользуется каждым следующим отчётом. Пример применения — `weekly/2026-08-04/REPORT.md`.
> Каркас (Marp, один markdown-файл на отчёт) взят от прежней презентации проекта
> `docs/artifacts/presentation_weekly.md`; **тема и палитра — свои, СВЕТЛЫЕ** (§4).
>
> ⚠ **Решение владельца от 2026-08-04:** отчёты зоны P делаются в **светлых тонах — и слайды,
> и графики**. Прежний тёмный вариант (первая редакция этого манифеста) отменён, возвращать
> его нельзя без нового явного указания.

---

## 1. Формат и сборка

Исходник отчёта — **один markdown-файл с Marp-фронтматтером** (`REPORT.md`). Слайд = блок между
`---`. Никаких бинарных «мастеров» — отчёт остаётся diff-абельным и читается прямо в GitHub/IDE,
даже если его никто не собирал.

```powershell
# сборка (по желанию; в git собранные файлы не идут — см. .gitignore)
npx @marp-team/marp-cli@latest research/presentations/weekly/<дата>/REPORT.md -o out.html
npx @marp-team/marp-cli@latest research/presentations/weekly/<дата>/REPORT.md --pptx -o out.pptx
```

**Структура каталога одного отчёта:**

```
weekly/<ISO-дата>/
├── REPORT.md          # сама презентация (Marp)
├── SOURCES.md         # трассировка: число → артефакт-источник (обязателен)
└── figures/
    ├── pstyle.py           # ОБЩИЙ стиль графиков (палитра §4) — импортируют все скрипты
    ├── make_figures.py     # сводные графики ИЗ ЛИТЕРАЛОВ, вписанных из журнала
    ├── make_overlay.py     # график ПО ДАННЫМ: наложение модели и измерений (см. §4а)
    ├── make_micrographs.py # обработка фотографий из зоны валидации (см. §4а)
    └── *.png               # результат
```

Все скрипты запускаются **из корня репозитория** и сами вычисляют путь к нему
(`REPO = Path(__file__).resolve().parents[4]`).

## 2. Каркас недельного отчёта (проверенная последовательность слайдов)

⚠ **Решение владельца от 2026-08-04: слайдов должно быть МАЛО.** Первая редакция отчёта была на
22 слайда и признана избыточной; рабочий объём недельного отчёта — **8 ± 2 слайда**. Всё, что не
влезло, живёт не в презентации, а в `SOURCES.md` и в журнале.

| # | Слайд | Зачем |
|---|---|---|
| 1 | Титул: период + **предмет недели** одной фразой и его паспортными числами | владелец должен понять итог, не листая |
| 2–3 | **Что измерено — картинкой**: наложение модели и данных, линейная шкала и децибелы | самый понятный слайд; показывает не «мы работали», а что именно получилось |
| 4 | Объяснение расхождения/эффекта, увиденного на слайдах 2–3 | сначала факт на графике, потом причина словами |
| 5–N | По одному слайду на закрытый шаг: **вопрос → как проверяли → число → что это значит** | |
| N+1 | По ролям A/B/C/D/L: кто что сделал; «нет активности за период» — писать явно | |
| N+2 | Что дальше / что решает владелец | |

Отрицательные результаты и **отозванные числа** в коротком формате не получают отдельного
слайда — их помечают прямо там, где число упомянуто (`**отозвано**`), а полный список ведётся
в `SOURCES.md`. Терять их нельзя: они дороже положительных.

## 3. Регистр текста (CHARTER §11, но короче, чем в `DRAFT.md`)

- **Сначала суть, потом формализм.** Абзац начинается с фразы «что это значит», а не с формулы.
- **Термин при первом употреблении — определяется тут же**, в скобках или врезкой `> 💡`.
  Врезки `> 💡` — образовательный слой; в отчёт для владельца они ИДУТ (в статью D — нет).
- **Число без источника не пишется.** В слайде число, в `SOURCES.md` — откуда оно.
- **Неопределённость называется вслух:** «тенденция, не результат», «не проверено» ≠ «проверено и
  чисто», «отозвано». Слайд без оговорок там, где они есть в журнале, — брак.
- **Английские термины** сохраняются в оригинале (`multistart`, `bootstrap`, `AIC`), но при первом
  употреблении — с русским пояснением.
- Одна мысль — один слайд. Больше 6 буллетов на слайде = слайд надо делить.

## 4. Палитра и правила графиков

Единственный источник истины по цветам графиков — **`figures/pstyle.py`**; ниже те же значения
словами. Слайд и график имеют один фон, поэтому картинка не «висит прямоугольником» на странице.

**Поверхность:** слайд `#f8fafc`, полотно графика `#ffffff`; основной текст `#0f172a`,
вторичный `#475569`, сетка `#cbd5e1`, заголовки `#0b5aa8`, заливка врезок `#f1f5f9` / `#e8f2fc`.

**Категориальные слоты (в фиксированном порядке, НЕ по кругу):**

| Слот | Цвет | Роль в отчётах P |
|---|---|---|
| 1 | `#2a78d6` синий | основная измеренная величина (эксперимент) |
| 2 | `#eb6834` оранжевый | сравниваемая/конкурирующая величина (модель) |
| 3 | `#1baf7a` зелёный | третья серия |
| — | `#64748b` серый | опорные линии, законы, эталоны (НЕ серия данных) |

Палитра прогнана валидатором навыка `dataviz` на этой поверхности
(`validate_palette.js "#2a78d6,#eb6834,#1baf7a" --mode light --surface "#ffffff" --pairs all`):
светлотная полоса PASS, порог цветности PASS, разделение при дальтонизме (худшая пара ΔE 9.2)
PASS, нормальное зрение (ΔE 24.0) PASS. **Одно известное исключение:** контраст слота 3 к белому
= 2.82 : 1 при пороге 3 : 1 → для него действует **правило рельефа** — у зелёной серии всегда
есть прямая подпись рядом с данными либо строка в таблице на том же слайде, идентичность не
держится на одном цвете. Пробовали заменить на `#008300` — валидатор завалил разделение при
протанопии (ΔE 3.2), вариант отклонён. Менять цвета «на глаз» нельзя: при замене — перепрогнать
валидатор.

**Жёсткие правила (нарушение = график переделывается):**

1. **Никогда две оси Y.** Разномасштабные величины — два графика или общая нормировка.
2. **Цвет закреплён за сущностью, не за рангом.** Убрали серию — оставшиеся не перекрашиваются.
3. **Легенда при ≥2 сериях обязательна**; при ≤4 сериях — плюс прямые подписи, чтобы идентичность
   не держалась на одном цвете.
4. **Тонкие штрихи:** линии 2 px, маркеры ≥8 px, сетка приглушённая и позади данных.
5. **Подписи — текстовым цветом**, не цветом серии.
6. **Последовательная шкала = один тон светлый→тёмный; расходящаяся = два тона + серый центр.**
   Радуги нет никогда.
7. **Числа на графике = числа в `SOURCES.md`.** Скрипт содержит литералы с комментарием-источником
   и не имеет доступа к `data_pool/`.

8. **Минимум врезок на самом графике.** Отдельное указание владельца (2026-08-04): «точки прямые
   и достаточно», объяснение — **текстом на слайде**, а не выносками поверх данных. Допустима
   максимум одна аннотация, и только если она не перекрывает ни одной точки. Первая редакция
   fig1/fig4 была переделана именно по этой причине.

**Чего в отчётах P не бывает:** круговых диаграмм долей, 3D, градиентных заливок под линией
«для красоты», подписи значения у каждой точки (только у ключевых), выносок-облачков поверх
данных.

## 4а. Графики ПО ДАННЫМ — когда можно (разрешение владельца 2026-08-04)

По умолчанию зона P не считает ничего (`STATE.md` п.1, 3). **Владелец 2026-08-04 выдал явное
разрешение:** «разрешаю писать и исполнять любые скрипты для построения графиков на основе
данных из зон других чатов». Это исключение узкое, и границы его такие:

- **Можно:** читать `data_pool/`, импортировать модель и загрузчики других зон, чтобы
  ПОСТРОИТЬ картинку.
- **Нельзя:** фитить и вообще получать новые числа. Параметры модели берутся **готовыми** из
  опубликованного артефакта зоны-автора (пример: `make_overlay.py` восстанавливает
  `lmfit.Parameters` из `a7_purewave.json` и не делает ни одного шага оптимизатора).
- **Нельзя:** писать что-либо вне `research/presentations/**`.
- **Обязательно:** в шапке такого скрипта — врезка «⚠ ОСОБЫЙ СТАТУС» с указанием, на каком
  разрешении он работает, что берёт готовым и чего не делает; и такая же оговорка в `SOURCES.md`.
- Числа, которые скрипт печатает в консоль (напр. «69 из 88 частот»), можно приводить на слайде
  как **свойство картинки**, а не как научный результат.
