# track_viewer — контроль углового прогона THz-TDS

Инструмент оператора у спектрометра: показывает угловую зависимость пропускания
**прямо во время съёмки** и раскладывает «дорогу» пустых файлов под следующий прогон.

**Зона C.** ТЗ — `docs/artifacts/C_TZ_tds_track_viewer.md`, согласовано с владельцем
2026-08-12. Открытые вопросы O-1…O-7 из §8 ТЗ закрыты владельцем в тот же день; решения
перечислены ниже и в `coordination/ACTIVITY.md`.

## Зачем

Качество прогона сейчас видно только постфактум, после обработки в `unified_optimizer`.
Съехавший образец, перепутанные `sig`/`bg` или испорченная трасса обнаруживаются через
часы или дни, когда прогон уже не переснять. Прецедент задокументирован: `test_grid_40_20`
дал `T = 105.7 %` из-за перепутанных файлов, и это едва не ушло в отчёт.

Это **контроль съёмки**: `unified_optimizer` не импортируется вовсе, числа с ним
сверяются, но не берутся у него.

Запрет ТЗ §9 на подгонку модели **снят владельцем 2026-08-13**. Инструмент подгоняет
угловую зависимость линеаризованным законом Малюса и показывает пропускание двух
каналов, утечку и угол столика. Метод — зоны A (`A0_malus_linearization`), порт
сверяется с оригиналом бит-в-бит. Геометрия и материальные параметры остаются в ядре
и здесь не извлекаются: угловой скан на одной частоте ограничивает не более пяти
вещественных чисел, и геометрии среди них нет.

## Запуск

```powershell
# из корня репозитория
.venv\Scripts\python.exe -m track_viewer.gui                       # окно
.venv\Scripts\python.exe -m track_viewer.gui data_pool\test_grid_33_11
.venv\Scripts\python.exe -m track_viewer.cli data_pool\purewave    # консоль
.venv\Scripts\python.exe -m track_viewer.cli <каталог> --csv трек.csv
.venv\Scripts\python.exe -m track_viewer.cli <каталог> --parseval --int-band 0.3 1.2
.venv\Scripts\python.exe -m track_viewer.cli <каталог> --noise dark
.venv\Scripts\python.exe -m track_viewer.cli <каталог> --fit --fit-spectral
.venv\Scripts\python.exe -m track_viewer.cli <каталог> --fit --fit-weights uniform
.venv\Scripts\python.exe -m track_viewer.selftest                  # приёмка, 36 проверок
```

Инструменты разработчика (в поставку не входят):

```powershell
.venv\Scripts\python.exe track_viewer\tools\check_py38.py       # совместимость с 3.8
.venv\Scripts\python.exe track_viewer\tools\smoke_gui.py        # прогон интерфейса
.venv\Scripts\python.exe track_viewer\tools\make_win7_kit.py    # сборка комплекта Win7
```

## Устройство

| Файл | Что внутри |
|---|---|
| `core/compat.py` | своя трапеция: `np.trapz` удалён в numpy 2, `np.trapezoid` отсутствует в 1.21 |
| `core/scan.py` | каталог прогона → список трасс; отбор по журнальной нумерации, кэш |
| `core/physics.py` | `T` во времени и по полосе, окно, пик, референс, шумовой пол |
| `core/fit_malus.py` | гармонический базис, замкнутые формулы каналов, побинный фит |
| `core/road.py` | генератор дороги пустых файлов и гардрейлы §5.2 |
| `gui.py` | Tkinter + matplotlib: 4, 6 или 8 панелей, слайдер, панель данных, окно генерации |
| `cli.py` | то же ядро без окна: печать трека, выгрузка CSV |
| `selftest.py` | приёмка §7 ТЗ, 36 проверок |

**Инвариант: в `core/` нет ни `tkinter`, ни `matplotlib`.** Благодаря этому вся приёмка
проходит без графического окружения. Проверяется машинно, тестом, а не договорённостью.

## Фаза 2 — решения владельца 2026-08-12

| Вопрос | Решение |
|---|---|
| компоновка панелей дельты | три ряда, средний узкий, сразу под угловыми |
| полоса интегрирования | **отдельная** от полосы показа, заливкой на спектре |
| `dark` в генераторе | настраиваемо; по умолчанию в начале и в конце |
| источник шумового пола по умолчанию | **ВЧ-хвост спектра (по Нафтали)** |

Что добавлено: пропускание по полосе частот рядом с временны́м и их разность
(`docs/track_viewer/01_FORMATS.md` §5.4–5.5), три источника шумового пола и
канал перекрытого пучка (§6.1–6.2).

Смена умолчания по шумовому полу — следствие измерения, а не вкуса: на
`002_bg.txt` предымпульсная оценка даёт `3.94·10⁻³` против `2.25·10⁻⁴` по
ВЧ-хвосту, то есть прежняя линия была на **12.4 дБ выше** реального шума.

## Фаза 3 — линеаризованный фит закона Малюса, решения владельца 2026-08-13

| Вопрос | Решение |
|---|---|
| запрет ТЗ §9 на подгонку модели | **снят** |
| что в среднем ряду Δ | разность двух подогнанных функций поверх точек Δ |
| спектры каналов `\|t⊥\|²(ν)`, `\|t∥\|²(ν)` | **свой ряд панелей** |
| веса МНК | переключатель; по умолчанию рецепт сессии A, `σᵢ ∝ Uᵢ` |

Подгонка линейная не из экономии, а потому что она **точна**: наблюдаемая
нелинейна по углу, но линейна по коэффициентам гармонического базиса. Решение —
одно нормальное уравнение, 33 мкс на трек, ковариация аналитическая. Метод — зоны
A (`research/two_wgp/NOTE_malus_linearization.md`), в `core/fit_malus.py` он
**скопирован**, а не импортирован: комплекта Win7 каталог `research/` не содержит.
Копию сверяет `tools/verify_fit_malus.py` — 48 сверок, расхождение `0.000e+00`.

Порядок базиса **4, а не 2**. Схема складывает поля и лишь потом берёт квадрат,
поэтому точный базис пятимерный, а фаза утечки входит только через 4-ю гармонику.
Разница не академическая: на `test_grid_33_11` порядок 2 даёт экстинкцию
`17.06 дБ` против `28.20` и `η = 0.140` против `0.0389`.

**Модель частотной зависимости не нужна.** Сумма по частотам сохраняет порядок
многочлена, поэтому `T(θ)` фитируется при любом поведении `t⊥(ν)`. Проверено
тождеством: коэффициенты широкополосного фита совпали со спектрально-взвешенным
средним 190 побинных до `4.7·10⁻¹³`. Отсюда и трактовка: широкополосный фит даёт
`⟨|t⊥|²⟩` со спектральным весом мощности референса, а не значение на частоте.

Числа сошлись с сессией A: `θ₀ = −1.2822°` из 2-й гармоники и `−1.2769°` из 4-й
против `−1.2770° ± 0.0354` у A13; `A₄/A₂ = 0.2509` при идеальных `0.25`.

## Обкатка комплекта на Windows 10/11

Комплект `../win7_track_viewer_kit` работает и на современной Windows — обкатать
его стоит до похода к прибору. Порядок тот же, но с одной особенностью: на рабочем
ПК Python обычно уже стоит, другой версии, а колёса в `wheels/` собраны **только
под 3.8**.

Поэтому `.bat`-файлы комплекта ищут интерпретатор явно (`_findpy.bat`): сначала
`py -3.8` через лаунчер, затем голый `python` — но лишь если это действительно 3.8.
Если 3.8 не найден, установка останавливается и называет найденную версию.

Без этой проверки `install.bat` положил бы колёса `cp38` в чужой Python и упал бы
с невнятной ошибкой pip, а `start.bat` запустился бы под ним же. На целевой машине
у прибора Python один, и проблема не проявлялась.

## Что инструмент не делает

* не обращается к `unified_optimizer`;
* не извлекает геометрию (`P`, `D_eff`) и не подбирает материальные параметры —
  это предел информации углового скана, а не недоделка;
* не работает в дБ при подгонке: логарифм от многочлена — не многочлен, и
  линейность разрушается (rms 1.73 дБ). Логарифм только для показа;
* не изменяет и не удаляет измеренные трассы ни при каких настройках;
* **не вычитает `dark` из трасс** — шум некогерентен, вычитание добавило бы второй
  экземпляр шума вместо того, чтобы убрать первый; `dark` идёт только в оценку уровня;
* пишет в каталог данных только пустые файлы, `META.txt` и `README.md`, и только при
  явной генерации дороги;
* не обновляется по таймеру — чтение каталога в момент записи трассы прибором вернуло бы
  обрезанный файл;
* не заменяет `MEASUREMENT_ORDER.md` и предполётный чек-лист: центровка образца
  проверяется руками, инструмент этого не видит.
