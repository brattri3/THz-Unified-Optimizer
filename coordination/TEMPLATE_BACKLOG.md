## [2026-08-05, O6] Таймстамп `.lock` никогда не обновляется

**Категория:** `generic-bug` | **Статус:** `open`

§12 п.2 прямо запрещает трогать `.lock` после занятия — heartbeat живёт только в
человекочитаемом блоке `sessions/<ID>.md`, который `preflight.py` по конструкции не читает
(читает только сам файл `.lock`: держатель + время создания). Следствие: любая сессия,
работающая дольше таймаута (15 мин), при проверке `inspect`/`acquire` выглядит просроченной —
и конкурентный чат получил бы код `1` (реклейм разрешён), хотя роль фактически жива и занята.
Вскрыто на практике `preflight.py ORCH` (read-only inspect) по живой сессии O6, 2026-08-05:
заход длился больше 15 минут, инструмент честно показал «ПРОСРОЧЕНО», хотя держатель (O6) не
менялся и работа не прерывалась. Не привело к инциденту только потому, что второго чата под
ролью ORCH в этот момент не было.

Планируемое решение при извлечении: операция продления (`--touch`, обновляет только время
файла `.lock`, не держателя) + отдельный сценарий в `stress_test_lock.py`, проверяющий, что
`--touch` не даёт постороннему чату реклейм даже при истёкшем старом таймстампе. Не чинить
здесь и сейчас — по решению владельца, `--touch` делается следующим заходом.

## [2026-08-05, O6] Двойной `--resume` одной сессии смешивает транскрипты

**Категория:** `generic-bug` | **Статус:** `open`

По документации Claude Code: если одну и ту же сессию возобновить (`--resume`) в двух
терминалах одновременно без явного ветвления, сообщения из обоих становятся частью ОДНОГО
файла транскрипта (`~/.claude/projects/**/*.jsonl`) — session id общий, порядок сообщений
внутри файла отражает порядок отправки, а не то, из какого терминала они пришли.

Для модели протокола «один ник = одна физическая беседа» (см. `NICKS.md`, обоснование через
раскопку реальных `session id` 2026-07-31 и повторно 2026-08-05 при переходе O5→O6) это
отдельный, ещё не описанный способ сломать учёт: два человека (или один человек в двух окнах)
могут работать под ОДНИМ ником одновременно, и `preflight.py`/`.lock` этого не поймают —
атомарность `.lock` защищает от двух РАЗНЫХ чатов, но не от двух терминалов ОДНОЙ и той же
resumed-сессии, которая для протокола выглядит как один держатель. В `NICKS.md` про этот
случай сейчас не сказано ничего.

При извлечении: либо явное правило в шаблоне («не возобновлять одну сессию параллельно в двух
терминалах»), либо осознанно принятое ограничение с описанием, почему `.lock` от него не
защищает. Не чинить здесь — фиксация находки, не решение.
