# CHARTER — мультиагентная сессионная работа над THz-Unified-Optimizer

> **ОБЯЗАТЕЛЬНО к прочтению первым в КАЖДОЙ рабочей сессии.** Это общий входной файл
> настроек и правил. Он определяет: кто ты, где твоя зона, как метиться, как обмениваться
> информацией, как коммитить, что делать при выходе за рамки. Дорабатывается оркестратором.

## 0. Зачем это
Над проектом одновременно работают несколько сессий-агентов (A/B/C/D + оркестратор ORCH),
разделяющих ОДИН git-репозиторий и `data_pool/`. Без протокола они затирают файлы друг друга,
конфликтуют в git и дублируют работу. Этот чартер — «правила дорожного движения».

## 1. Кто ты (идентичность)
Твой ID (A/B/C/D/ORCH) задаётся В ЛАУНЧ-ПРОМТЕ сессии. Если не задан — СПРОСИ у владельца, не
работай анонимно. Прочитав чартер, ты обязан:
1. Обновить свою строку в `coordination/BOARD.md` (статус, текущая задача, план, время).
2. Обновить `coordination/sessions/<ID>.md` (что делаю, какие файлы трогаю, до какого времени).
3. Работать ТОЛЬКО в своей зоне (§3). Логировать изменения в `coordination/ACTIVITY.md`.

## 2. Модель изоляции (git) — гибрид
- **Общий рабочий каталог на `main`** для того, что требует ЖИВЫХ общих данных/состояния:
  анализ (A, D), `data_pool/` (read-only), `research/logs`, `research/state.json`.
- **Worktree + отдельная ветка** РЕКОМЕНДУЕТСЯ для сессий, активно правящих ОБЩИЙ КОД
  (B — рефактор ядра) или изолированных (C — приложение): `git worktree add ../TUO-<ID> session/<ID>`,
  запуск `claude` В ЭТОМ каталоге. Оркестратор мержит в main. (Практика: не запускать двух
  правящих один и тот же код сессий в одном каталоге.)
- Если сессия остаётся в общем каталоге — она НЕ создаёт свою ветку (все на `main`),
  а соблюдает владение (§3) и «анонс перед коммитом» (§5).

## 3. Зоны ответственности (владение путями)
См. полную карту в `coordination/OWNERSHIP.md`. Кратко:
| Сессия | Специализация | Владеет (пишет) | Читает |
|---|---|---|---|
| **A** | двух-WGP модель + софт затухания | `research/two_wgp/`, `research/results/two_wgp/` | model_blanco, fit_lib, model_core |
| **B** | инфра/рефактор ядра | `research/experiments/model_core.py`, `verify_*`, рефактор `research/experiments/*.py` | всё research |
| **C** | приложение-прототип | `attenuator_app/`, `docs/attenuator_app/` | model_blanco, research/two_wgp |
| **D** | статья | `research/paper/` | SYNTHESIS, RESEARCH_LOG, results |
| **ORCH** | контроль/мерж/координация | `coordination/`, `CLAUDE.md`, main `research/state.json`, ветки/мержи | всё |
**Правило shared-кода:** общие модули (`fit_lib.py`, `model_core.py`, `model_blanco`) правит ТОЛЬКО
владелец (B). Другим — read-only; нужна правка → запрос через `ACTIVITY.md` + `HANDOFFS.md`, ждать B.

## 4. Общая зона обмена (координация)
- `coordination/BOARD.md` — ЖИВОЙ статус всех сессий (обновляй свою строку при старте, смене задачи,
  раз в ~несколько шагов = «пульс», при остановке).
- `coordination/ACTIVITY.md` — append-only журнал изменений/планов МЕЖДУ сессиями: что изменил, зачем,
  какие файлы, что это значит для других. Пиши сюда ПОСЛЕ значимого изменения.
- `coordination/sessions/<ID>.md` — твой «замок намерений»: старт-метка + план + файлы, что трогаешь,
  до какого времени. Перед правкой ОБЩЕГО файла — проверь чужие sessions/*.md на конфликт.
- `coordination/HANDOFFS.md` — запросы «сделай в другой зоне» (см. §6).

## 5. Коммиты — обязательная разметка
- Префикс сообщения: **`[<ID>] краткое что`** (напр. `[A] two-WGP attenuation calc A4`).
- Трейлеры в конце сообщения:
  ```
  Session: <ID>
  Reason: <почему сделан коммит>
  Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>
  ```
- Коммить ТОЛЬКО файлы своей зоны (`git add <свои пути>`), не `git add -A` вслепую.
- **Анонс перед коммитом на общий main:** отметь в `ACTIVITY.md` (сессия, файлы, причина) — чтобы
  другая сессия не запушила поверх. При работе в worktree/ветке — коммить свободно, мерж делает ORCH.
- Перед push: `git pull --rebase` (если на общем main). Конфликт общего файла → не форсить, звать ORCH.

## 6. Выход за рамки зоны — НЕ ДЕЛАЙ, перенаправь
Если владелец просит тебя сделать то, что вне твоей специализации/зоны:
1. НЕ выполняй. Кратко объясни, что это зона Сессии `<Y>`.
2. Запиши запрос в `coordination/HANDOFFS.md` (от кого, кому, что нужно, контекст).
3. Предложи владельцу: «переключись в Сессию `<Y>`» ИЛИ «создать новую сессию `<Z>`» с готовым
   лаунч-промтом (шаблон — в `coordination/LAUNCH_PROMPTS.md`).
Исключение: тривиальное чтение/справка — можно, но правки в чужой зоне — только через хэндофф.

## 7. Протокол одной итерации (в дополнение к research/state.json)
1. Прочитать CHARTER (этот файл) + свой `sessions/<ID>.md` + `BOARD.md` (нет ли пересечений).
2. Прочитать свой рабочий `state.json` (напр. `research/two_wgp/state.json`) → первая не-done задача.
3. Проверить: файлы, что буду трогать, не заявлены другой активной сессией. Если заявлены — взять
   другую задачу или согласовать через ACTIVITY.
4. Заявить намерение в `sessions/<ID>.md`, выполнить ОДИН атомарный шаг.
5. Числа → `research/logs/RESEARCH_LOG.md` с тегом `[<ID>]`. Изменение → `ACTIVITY.md`.
6. Обновить свой `state.json` и строку в `BOARD.md` (пульс).
7. Гардрейлы `research/RESEARCH_PLAN.md §6` действуют всегда.

## 8. Разрешение конфликтов
- Устаревший «замок» (sessions/<ID>.md heartbeat старше ~1 ч) → считать сессию неактивной, ORCH
  снимает замок.
- Пересечение зон/двойная работа → ORCH арбитр; при отсутствии ORCH — владелец решает.
- Общий файл нужен двум → сериализовать через ACTIVITY (кто первый заявил), второй ждёт.

## 9. Оркестратор (ORCH) — опционально, но рекомендуется
Отдельная сессия-контролёр: читает BOARD/ACTIVITY/sessions, снимает устаревшие замки, мержит ветки
worktree в main, разруливает конфликты общих файлов, поддерживает CHARTER/OWNERSHIP в актуальности,
назначает/перенаправляет задачи. Спец и лаунч — `coordination/ORCHESTRATOR.md`.

## 10. Доработка
Этот чартер — живой. Предложения по улучшению парадигмы → в `ACTIVITY.md` с тегом `[proposal]`;
ORCH консолидирует и правит CHARTER (это его зона).
