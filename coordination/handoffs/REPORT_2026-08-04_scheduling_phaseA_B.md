## 1. Фаза A — эмпирический тест Планировщика Windows

**Единственный пункт, без которого весь механизм автономного пробуждения — гипотеза, а не план**
(формулировка плана). Проверено реальным прогоном, не симуляцией.

### Как проверялось
- Разовая задача `schtasks /create /sc once`, время старта — «сейчас + 2 минуты».
- Задача запускала `.cmd`-обвязку (`scheduler_test.cmd` в scratchpad), которая:
  1. Пишет метку времени `FIRED:` в лог сразу при старте.
  2. Запускает **headless** `claude.exe -p "Answer with exactly one word: OK" --model haiku
     --dangerously-skip-permissions` (полный Windows-путь `C:\Users\ps656\.local\bin\claude.exe`,
     чтобы не зависеть от PATH в контексте Планировщика), вывод — в тот же лог.
  3. Пишет метку `DONE:` по завершении.

### Находка №1 — реальный баг, не гипотетический
Первая попытка создать задачу (`/sd 08/04/2026`, формат `MM/dd/yyyy`) дала предупреждение
`WARNING: Task may not run because /ST is earlier than current time` и `Next Run Time: N/A`.
Причина: эта машина — локаль **`ru-RU`**, `ShortDatePattern = dd.MM.yyyy`. Дата `08/04/2026`
была молча разобрана как «8 апреля 2026» (уже прошедшая), а не «4 августа». **Если бы это не
было замечено проверкой `Next Run Time` до ухода в ожидание — задача никогда бы не сработала,
без единой явной ошибки.** Это ровно тот «тихий отказ», которого план и опасался (§0 плана) —
только источник оказался не в правах/сессии, а в локали формата даты.

**Исправление:** дата передана в формате текущей культуры (`(Get-Date).ToString('dd.MM.yyyy')`).
После этого `Next Run Time` показал верное время, задача сработала штатно.

### Результат замера (один прогон, после исправления)
| Метка | Время | Что значит |
|---|---|---|
| Плановое время | `22:51:00` | что было заказано `schtasks` |
| `Last Run Time` (журнал `schtasks`) | `22:51:19` | движок Планировщика запустил процесс — **дрейф ≈19 с** |
| `FIRED:` (первая строка `.cmd`) | `22:51:22,17` | ещё **≈3 с** на старт `cmd.exe` |
| `DONE:` (после `claude -p`) | `22:51:31,24` | сама headless-сессия claude заняла **≈9 с** |

- **Итого от плана до полного завершения: ≈31 с.**
- `claude -p` вернул ровно `OK` (запрошенный формат соблюдён).
- `schtasks`-код результата (`Last Result`): `0` (успех).
- Задача одноразовая, удалена сразу после проверки (`schtasks /delete /f`) — в системе не
  осталась.

### Что НЕ проверено (честно как пробел, не выдаю за покрытое)
- **Заблокированный экран** — сессия владельца была активна и разблокирована весь тест;
  специально блокировать экран означало бы прервать текущую рабочую сессию, не сделано. Это
  именно тот сценарий, который план называет «частым источником тихого отказа у Task
  Scheduler» — вопрос остаётся открытым.
- **Дрейф на серии срабатываний подряд** — план предлагал повторный тест с интервалом; сделан
  только один разовый прогон.
- **Устойчивость к перезагрузке/сну машины** между планированием и срабатыванием.

Полный разбор — `coordination/SCHEDULING.md §7a` (новый раздел).

## 2. Фаза B, пп.1-2 — два открытых вопроса, разобраны решением (не кодом)

По формулировке плана: «каждый — с опорой на то, что уже реально работает». Новых файлов/кода не
заводил — только аргументированная правка `SCHEDULING.md §2a` (новый раздел) и обновление статуса
пп.1-2 в §8.

### П.1 — ширина окна планирования vs таймаут `.lock` (15 мин)
**Вывод: это два разных масштаба времени и разное назначение, путать не стоит.**

- Таймаут `.lock` (CHARTER §12) отвечает на вопрос «жив ли этот конкретный чат прямо сейчас» —
  порог **обнаружения сбоя**, короткий по конструкции. Фаза A сегодня дала конкретную цифру на
  той же оси: даже тривиальный headless-перезапуск `claude -p` съедает ≈9-31 с сам по себе —
  заметная доля от 15 минут, если бы окно и таймаут были одним числом.
- Ширина окна планирования отвечает на другой вопрос — «сколько проекту позволено уйти вперёд,
  прежде чем владелец должен посмотреть» — порог **человеческого темпа**. Должна вмещать
  реальный «один атомарный шаг» (CHARTER §7) содержательной работы; `kpi_data.json` (снимок
  2026-07-31) показывает, что содержательные сессии ролей идут часами с десятками
  Bash/Edit-вызовов за заход — на порядок дороже, чем факт «процесс жив».

**Рекомендация ORCH (не решение — документ явно требует подтверждения владельца):** активное
окно **30 минут** / окно тишины **10 минут** как стартовый дефолт. Цифра НЕ откалибрована по
реальному распределению длительности «одного атомарного шага» по ролям — это отдельная задача
(возможно, часть будущей Фазы C), сегодня не делалась.

### П.2 — HARD_STOP или PING_CONTINUE по умолчанию
**Рекомендация ORCH: `HARD_STOP` — дефолт**, `PING_CONTINUE` — явный opt-in флагом для
конкретной роли/захода.

Довод — от собственной формулировки документа (`SCHEDULING.md §2`): окна это «предохранитель, не
оптимизация», цель явно сформулирована как «проект не убежит быстрее, чем я успеваю следить».
`PING_CONTINUE` эту гарантию ослабляет: если владелец не увидел пуш-уведомление сразу (сон,
недоступность), проект может уйти на несколько атомарных шагов вперёд до следующего окна тишины
— именно тот сценарий, от которого окна должны страховать. `HARD_STOP` держит гарантию буквально,
ценой простоя сессии в ожидании.

Оба пункта — рекомендации с явным обоснованием, **не финальные решения**: `SCHEDULING.md`
остаётся черновиком (см. шапку самого файла), реализация (CHARTER §13 и т.д.) — только после
подтверждения владельцем.
