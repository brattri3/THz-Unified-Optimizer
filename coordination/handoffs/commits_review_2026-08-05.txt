+# SCHEDULING — окна работы, роль SEC, автономный режим (ПРОЕКТ, ждёт одобрения владельца)
+
+> **Статус: ЧЕРНОВИК.** Ничего из описанного здесь ещё не введено в действие — ни в
+> `CHARTER.md`, ни в виде реального кода/задач Планировщика. Документ сводит воедино
+> решения, принятые в разговоре с владельцем 2026-07-31, для вычитки и правки. После
+> одобрения: (1) появляется CHARTER §13 со ссылкой сюда, (2) реализуются файлы-механизмы
+> ниже, (3) регистрируется сессия SEC по обычной процедуре (NICKS/BOARD/sessions).
+
+## 0. Зачем это вообще
+
+Мультисессионная работа над проектом (сессии A/B/C/D/L + ORCH) может в перспективе идти
+автономно, по расписанию, без владельца за клавиатурой. Но владелец хочет: (а) не терять
+контроль над скоростью эволюции проекта, (б) успевать вмешаться или прислать сигнал
+остановки, (в) не тратить общий 5-часовой лимит подписки Pro впустую из-за того, что
+несколько сессий одновременно запустили дорогие расчёты. Отсюда — три независимых, но
+переплетённых механизма: **окна** (контроль темпа), **реестр резерваций** (контроль
+бюджета), **роль SEC** (клей между ними + канал уведомлений).
+
+## 1. Роль SEC — «секретарь и аналитик»
+
+Уже частично существует как инструмент (`coordination/tools/kpi_stats.py` +
+`kpi_report.py`, зона ORCH, коммит `c6dad19`). Проектом предполагается вырастить это в
+полноценную сессию-роль:
+
+- **Пишет:** `coordination/reports/**`, свой `sessions/SEC.md`, свои строки в
+  `NICKS.md`/`BOARD.md`/`ACTIVITY.md`, (после этого документа) `coordination/schedule.json`
+  и `coordination/QUESTIONS.md`.
+- **Читает:** всё координационное + `git log`. Не трогает `research/**`, `attenuator_app/**`
+  — она про процесс, не про науку.
+- **Никогда не делает:** не редактирует чужие локи, не форсит чужие решения — только
+  предлагает (запись в `ACTIVITY.md`/`QUESTIONS.md`) или сигналит (`PushNotification`).
+- **Обязательный preflight:** по договорённости — запускается ПЕРВОЙ при старте любой
+  сессии: собирает свежий KPI (`kpi_stats.py`), даёт сводку «что случилось, пока вас не
+  было», проверяет `/usage` (реальный остаток лимита текущего 5-часового окна — команда
+  `/usage`/`/status` встроена в Claude Code, это НЕ оценка по токенам, а факт от Anthropic)
+  и реестр резерваций (§3), даёт вердикт: можно стартовать / подождите окна / осторожно,
+  бюджет на исходе.
+- **Событийные правила** (пуш только при срабатывании, не по расписанию — решение
+  владельца):
+  1. Зависший лок (`IN_PROGRESS`, heartbeat старше 15 мин, CHARTER §12).
+  2. Коллизия — два чата одной роли одновременно `IN_PROGRESS` (прецедент L1/L2).
+  3. Кандидат на `/compact` (токены/длительность активного чата превысили порог).
+  4. Порог бюджета — оценка `$`/токенов по роли или по проекту с прошлой проверки.
+- **Стек:** Python stdlib (уже написан) + Planировщик Windows (`schtasks`) для запуска.
+  Инструменты сессии: `PushNotification`, `Artifact` (передеплой отчёта), Bash/Read/Grep.
+
+## 2. Окна — темп, не бюджет
+
+Смысл, зафиксированный владельцем: окна нужны **для контроля темпа со стороны владельца**,
+а не для экономии токенов (для этого есть реестр, §3). Ошибочно было бы решить, что окна —
+это оптимизация; это в первую очередь предохранитель «проект не убежит быстрее, чем я
+успеваю следить».
+
+- **Активное окно** (пример: 15 минут) — в это время могут работать зарегистрированные на
+  это окно сессии.
+- **Окно тишины** (пример: 5 минут) сразу после — доступ только ORCH/SEC. Используется для:
+  сбора заявок на следующее окно, вызова `/usage`, публикации расписания следующего окна.
+- **Два режима того, что значит «окно закрылось»** — оба нужны, переключаются флагом
+  (см. §5), а не архитектурно разные системы:
+  - **HARD_STOP** — сессия обязана физически остановиться на границе окна и ждать связи с
+    владельцем/следующего разрешения.
+  - **PING_CONTINUE** — SEC присылает статус на границе окна, работа продолжается до
+    ближайшего естественного атомарного шага (CHARTER §7 уже требует «один атомарный шаг за
+    итерацию» — это и есть точка паузы, ничего дополнительно изобретать не нужно).
+
+### 2a. Разбор открытых вопросов §8 пп.1-2 (Фаза B, 2026-08-04, песочница scheduling-dev)
+
+**П.1 — ширина окна ≠ таймаут `.lock` (15 мин). Это два разных масштаба, путать не стоит.**
+Довод: у них разное назначение и разная физика отказа.
+- Таймаут `.lock` (CHARTER §12) отвечает на вопрос «жив ли этот конкретный чат прямо сейчас»
+  — калиброван под то, сколько правдоподобно молчать между heartbeat-ами одного процесса,
+  прежде чем считать его упавшим. Короткий по конструкции, это порог ОБНАРУЖЕНИЯ СБОЯ.
+  Fаза A сегодня добавила конкретную цифру к этой же оси времени: headless-перезапуск
+  `claude -p` (даже тривиальный, `--model haiku`) занял ≈9 с целиком + ≈19-22 с дрейфа
+  запуска от Планировщика — то есть даже холодный пуск процесса съедает заметную долю
+  15-минутного окна, если бы окно и таймаут были одним числом.
+- Ширина окна планирования отвечает на другой вопрос — «сколько проекту позволено уйти
+  вперёд, прежде чем владелец должен посмотреть» — порог ЧЕЛОВЕЧЕСКОГО ТЕМПА, не сбоя.
+  Он должен вмещать реальный «один атомарный шаг» (CHARTER §7) содержательной работы
+  (правка кода, прогон фита, запись в лог) — это на порядок дороже по времени, чем сам факт
+  живого процесса; `kpi_data.json` (снимок 2026-07-31) показывает, что содержательные сессии
+  ролей длятся часами тратя десятки Bash/Edit-вызовов на один заход, не минутами.
+  **Вывод: НЕ переиспользовать 15 минут дословно.** Рекомендуемый стартовый дефолт —
+  **активное окно 30 минут, окно тишины 10 минут** (на порядок шире таймаута лока, чтобы
+  один реальный атомарный шаг гарантированно помещался, но короче настолько, чтобы владелец
+  успевал вмешаться в пределах одного присеста за компьютером). Цифра — начальная, не
+  калибрована по данным (это была бы Фаза C/задача §1 плана — нужна отдельная выборка
+  длительности «один атомарный шаг» по ролям, сегодня не собиралась); **владелец
+  подтверждает или поправляет перед тем, как цифра попадёт в CHARTER §13.**
+
+**П.2 — дефолт по умолчанию: HARD_STOP.** Довод от собственной формулировки документа (§2,
+выше): окна — это «предохранитель, не оптимизация», цель явно сформулирована как
+«проект не убежит быстрее, чем я успеваю следить». `PING_CONTINUE` этому соответствует
+слабее: если владелец не увидел пуш-уведомление сразу (сон, недоступность), проект может
+уйти на несколько атомарных шагов вперёд ДО следующего окна тишины — именно тот сценарий,
+от которого окна должны страховать. `HARD_STOP` даёт эту гарантию буквально ценой простоя
+сессии в ожидании. Рекомендация: **`HARD_STOP` — дефолт**, `PING_CONTINUE` — явный opt-in
+флагом для конкретной роли/захода, когда владелец сознательно даёт больше автономии (напр.
+известно дешёвая, низкориска задача). Как и п.1 — рекомендация ORCH, не решение: сам
+документ (см. шапку) требует одобрения владельца перед тем, как это станет действующим
+правилом CHARTER §13.
+
+## 3. Реестр резерваций — бюджет, не темп
+
+Цель — не дать нескольким сессиям одновременно съесть общий 5-часовой лимит Pro.
+
+- **Заявка** — лёгкая запись самой сессии в СВОЁМ `sessions/<ID>.md` (поле
+  `next_window_request: {задача, оценка_токенов/действий, приоритет}`), не общий файл —
+  чтобы не было гонки записи N чатов в одно время.
+- **SEC — единственный автор** `coordination/schedule.json` (машиночитаемый) и его
+  человекочитаемого зеркала на KPI-странице (§6). В окне тишины перед открытием окна SEC:
+  собирает все `next_window_request` → смотрит `/usage` → распределяет по приоритету →
+  публикует авторизованный список на окно (кто допущен, кто ждёт).
+- **Один активный чат на роль одновременно** (уже действующий инвариант CHARTER §12) —
+  сохраняется и внутри окна: разные РОЛИ могут работать параллельно в одном окне, но не два
+  чата одной роли.
+- **Дальний слот-«письмоноша»** — сессия может зарезервировать далёкий слот с
+  почти нулевой заявленной стоимостью ТОЛЬКО чтобы проверить, не пришло ли ей что-то в
+  `HANDOFFS.md`/ответ от другой сессии; если пришло — регистрирует уже полноценную заявку на
+  следующее подходящее окно, если нет — снова засыпает.
+
+## 4. Механизм запуска/пробуждения — факты, не предположения
+
+Проверено через `claude --help` и поведение инструментов в этом чате:
+
+- **`CronCreate`/`ScheduleWakeup`** — работают ТОЛЬКО внутри уже открытой сессии (само себя
+  будит). In-memory, **гибнут при `exit`/крахе чата**, `CronCreate` имеет жёсткий потолок
+  **7 дней** с автоудалением. Годятся ТОЛЬКО для роли, которая физически остаётся открытой
+  («припаркована») между окнами — не могут поднять уже закрытый чат.
+- **Планировщик Windows (`schtasks`) + headless `claude -p ...`** — единственный способ
+  поднять НОВЫЙ процесс для роли, чат которой закрыт. Переживает перезагрузку/сон,
+  не имеет 7-дневного потолка. Заявленная владельцем ненадёжность — **базовый тест сделан,
+  см. §7a, частично закрыт** (срабатывание подтверждено, экран/серия/сон — ещё нет).
+- **Решение по каждой роли — выбор владельца, не архитектурный факт:** держать чат
+  «припаркованным» (дешевле по перезапуску контекста, но хрупко к перезагрузке/сну машины и
+  ограничено 7 днями) ИЛИ закрывать и поднимать заново по расписанию (устойчивее, но каждый
+  раз «с нуля» по файлам состояния, не по памяти чата).
+
+## 5. Режим ATTENDED / UNATTENDED — что делать с вопросами к владельцу
+
+Проблема, которую поднял владелец: ночью (или когда он недоступен) сессия может зависнуть на
+`AskUserQuestion`-подобном опросе, ожидая ответа, который не придёт.
+
+- **Флаг** `coordination/MODE.flag`: `ATTENDED` (владелец у клавиатуры, вопросы — как
+  обычно) / `UNATTENDED` (владелец недоступен, переключает сам перед тем как оставить
+  проект без присмотра, например на ночь).
+- **В `UNATTENDED`** сессия применяет уже существующий критерий обратимости действия
+  (тот же, что в системных инструкциях по риску — не новое правило):
+  - Вопрос про **обратимое/некритичное** (выбор подхода, приоритет, стиль) → берёт разумный
+    дефолт, пишет его и причину в `coordination/QUESTIONS.md` (append-only, как
+    `HANDOFFS.md`), продолжает работу.
+  - Вопрос про **необратимое/дорогое/меняющее направление** → останавливается, SEC шлёт
+    `PushNotification` «сессия `<ник>` ждёт решения», ждёт ответа владельца (в т.ч. через
+    Remote Control с телефона — уже подтверждено рабочим).
+- **Флаг остановки** `coordination/STOP.flag` (наличие файла = сигнал) — про ДРУГОЕ: полная
+  приостановка планирования НОВЫХ окон проектом целиком (не ответ конкретной сессии на
+  конкретный вопрос — это обычный диалог, отдельного протокола не требует). SEC проверяет
+  этот флаг перед публикацией расписания каждого следующего окна.
+

+## 7a. Результат эмпирического теста Планировщика Windows (Фаза A, 2026-08-04, песочница scheduling-dev)
+
+**Базовый вопрос («срабатывает ли вообще headless-перезапуск») — ДА, подтверждено реальным
+прогоном, не симуляцией.**
+
+- Разовая задача `schtasks /create /sc once`, цель — `.cmd`-обвязка, запускающая
+  `claude.exe -p "..." --model haiku --dangerously-skip-permissions` headless и логирующая
+  метки времени до/после.
+- **Найден реальный баг настройки, не гипотетический:** `schtasks /create ... /sd MM/dd/yyyy`
+  с датой в формате US (`08/04/2026`) на этой машине (локаль `ru-RU`, `ShortDatePattern =
+  dd.MM.yyyy`) молча разобрался НЕВЕРНО — предупреждение `/ST is earlier than current time` +
+  `Next Run Time: N/A`, задача была бы создана, но никогда не сработала. Это ровно тот «тихий
+  отказ», которого план и опасался (§0 плана) — только источник оказался не в правах/сессии, а в
+  локали формата даты. Исправлено передачей даты в локальном формате (`dd.MM.yyyy` через
+  `(Get-Date).ToString('d')` под текущей культурой) — после этого `Next Run Time` показал верное
+  время, задача сработала.
+- **Замер после исправления (один прогон):**
+  - Плановое время: `22:51:00`.
+  - `schtasks`-журнал (`Last Run Time`): `22:51:19` → дрейф запуска процесса **≈19 с** от плана.
+  - Первая строка лога самого `.cmd` (`FIRED:`): `22:51:22,17` → ещё **≈3 с** на старт `cmd.exe`.
+  - `claude -p` (headless, `--model haiku`, тривиальный промт) отработал и вернул ровно `OK`
+    (запрошенный формат ответа соблюдён), заняв **≈9 с** до строки `DONE: 22:51:31,24`.
+  - Итого от плана до полного завершения: **≈31 с**. `schtasks`-код результата (`Last Result`) —
+    `0` (успех).
+  - Задача одноразовая, удалена сразу после `schtasks /delete /f` — не оставлена в системе.
+- **НЕ проверено этим прогоном (честно фиксируем пробел, не выдаём за покрытое):**
+  - Поведение при ЗАБЛОКИРОВАННОМ экране — сессия владельца была активна и разблокирована все
+    время теста; специально блокировать экран ради теста означало бы прервать текущую рабочую
+    сессию, не сделано. Это именно тот сценарий, который план называет «частым источником тихого
