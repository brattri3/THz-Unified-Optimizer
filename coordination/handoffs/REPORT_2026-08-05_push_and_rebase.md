## 3. Ответ по локу O6 (Задача 3)

**Да, O6 занимал лок через `preflight.py` на холодном старте этого захода** (первое сообщение
этого захода, ещё до Задачи 1 нынешнего промта — просто не попало текстом в предыдущий отчёт
`REPORT_2026-08-05_nicks_rebase.md`, который начинался сразу с Задач 1–2 того промта):

```
$ py coordination/tools/preflight.py ORCH --acquire O6
[preflight] ПРЕДУПРЕЖДЕНИЕ: ник 'O6' не найден в NICKS.md (зарегистрируй его ДО занятия лока
по конвенции CHARTER §12, но это не блокирует .lock).
[preflight] Роль ORCH: .lock не существовал -> СОЗДАН с нуля, держатель O6.
[preflight] РЕЗУЛЬТАТ: ЗАНЯТО ЭТИМ ВЫЗОВОМ (0). Можно приступать к работе под ролью.
EXIT_CODE=0
```

**Финальный `inspect` (сейчас, для этого отчёта):**

```
$ py coordination/tools/preflight.py ORCH
[preflight] Роль ORCH: держатель 'O6', взят 2026-08-05 12:16:37 (34.4 мин назад, таймаут 15 мин)
[preflight] РЕЗУЛЬТАТ: ПРОСРОЧЕНО. Реклейм разрешён (но не выполнен — это read-only режим).
EXIT=1
```

**Пояснение кода `1` здесь (не тревога):** заход идёт дольше 15-минутного таймаута §12, а
протокол (п.2 §12) обновляет на пульсе только человекочитаемый блок в `sessions/ORCH.md`, НЕ
трогая сам файл `.lock` (он создаётся один раз при занятии). Поэтому `inspect` честно показывает
«просрочено по времени файла» — это НЕ значит, что кто-то реклеймил роль: `.lock` по-прежнему
содержит `O6`, что и подтверждает вывод («держатель 'O6'»). Это read-only проверка, `--acquire`
