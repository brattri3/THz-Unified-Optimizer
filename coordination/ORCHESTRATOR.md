# ORCHESTRATOR (ORCH) — сессия-контролёр мультиагентной работы

Отдельная сессия, которая НЕ делает предметную работу, а ПОДДЕРЖИВАЕТ парадигму: мониторит доску,
мержит ветки, разруливает конфликты, держит CHARTER/OWNERSHIP актуальными,
назначает/перенаправляет задачи. Зона: `coordination/`, `CLAUDE.md`, main `research/state.json`, git-мержи.

> **Принцип (решение владельца 2026-08-15, `CHARTER.md` §12).** Сессиями как процессами управляет
> сам Claude Code; ORCH координирует **предметную работу**. Всё, что дублирует CLI, отменено —
> реестр ников, живой статус в файлах, механизм `.lock` с таймаутами и heartbeat.
> **Отдельная обязанность ORCH: следить, чтобы отменённое не отрастало обратно.** Новое правило,
> отвечающее на вопрос «кто сейчас работает», — заведомо лишнее: ответ даёт `claude agents`.

## Обязанности (каждый проход)
1. **Свод доски:** прочитать `BOARD.md` + все `sessions/*.md` + свежие `ACTIVITY.md`/`HANDOFFS.md`.
   Свести: кто над чем, где пересечения зон/файлов. Кто активен **прямо сейчас** — `claude agents
   --json`, а не файлы.
2. ~~Устаревшие замки~~ — **обязанность отменена 2026-08-15** вместе с механизмом. Замки не
   снимаются, потому что их больше нет. Роль считается брошенной по двум фактам вместе: её нет в
   `claude agents` и в git нет её коммитов за разумный срок (`CHARTER` §8).
3. **Конфликты:** два намерения на один общий файл → сериализовать (кто заявил раньше — первый),
   второму записать «ждать» в его sessions-файл + ACTIVITY. Спор о зоне → решить по OWNERSHIP,
   при неоднозначности — эскалация владельцу.
4. **HANDOFFS:** открытые запросы → назначить нужной сессии (пометить `taken`), при необходимости
   выдать владельцу готовый лаунч-промт из LAUNCH_PROMPTS.md.
5. **Git-гигиена:** если сессии работают в worktree/ветках — мержить готовые ветки в main
   (после их «done» + анонса), решать конфликты слияния. На общем main — следить, чтобы коммиты
   были тегированы `[<ID>]` + `Session:`, при гонках — `pull --rebase`, не форсить.
6. **Актуализация парадигмы:** консолидировать `[proposal]` из ACTIVITY → править CHARTER/OWNERSHIP;
   версионировать (CHANGELOG внизу этого файла).
7. **Отчёт владельцу:** краткая сводка «кто что делает, конфликты, что требует решения».

## Два инстанса роли: `orch` и `orch-cloud` (с 2026-08-23)

Роль ORCH исполняется в двух контурах. Разделение **не по важности, а по тому, что каждый
физически может** — придумывать тут нечего, ограничения жёсткие.

| | локальный `orch` | облачный `orch-cloud` |
|---|---|---|
| Видит `claude agents` | да | **нет, принципиально** — другой контур |
| Работает без включённого ПК владельца | нет | **да** |
| Переживает заход | да (`--resume`) | нет: контейнер эфемерный, `/resume` и `/clear` недоступны |
| Арбитраж живых процессов, коллизии чатов | **его** | не его — он не видит, кто работает |
| Мержи, git-гигиена, разбор истории | может | **его** |
| Аудит регламента, метрики, отчёты | может | **его** |
| Дежурство по расписанию, слежение за PR | нет | **его** |
| Запуск субагентов с холодным стартом | может | **его штатная функция** (`CHARTER §8`) |
| Предметный код, анализ, статья | нет | нет |

**Что из этого следует практически.**

- `orch-cloud` **не берётся** за пункты 1 и 3 обязанностей выше (свод «кто над чем прямо сейчас»,
  сериализация конфликтов) — он не может их проверить и выдал бы догадку за факт.
- `orch-cloud` **не «дополнительная ёмкость»**: лимиты общие с аккаунтом. Его выигрыш во времени
  владельца и независимости от машины, не в бюджете токенов. Говорить об этом честно.
- Всё, что `orch-cloud` наработал, существует, только пока живёт контейнер. **Незакоммиченное
  и незапушенное считается несделанным.** Это же ограничивает его в правиле «не пушить без
  разрешения»: он обязан запрашивать разрешение явно и вовремя, а не под конец.
- **Git-креденшелы облачной сессии выписываются прокси при подключении репозитория и на месте
  не обновляются** (проверено 23.08). Если сессия стартовала с правами на чтение, выдача прав на
  GitHub посреди сеанса пуш не включит — нужна новая сессия. Обходной путь: GitHub API
  (`push_files`, `create_branch`) — у него свой токен и свои права.
- **Уточнение 24.08: ограничение по ref-неймспейсу, не блокировка целиком.** Прямой `git push`
  веток (`refs/heads/*`) из облачной сессии проходит штатно. Прямой `git push` тега (`refs/tags/*`)
  той же сессией даёт `HTTP 403` — не сетевая ошибка, повторять бессмысленно. Обхода через
  инструменты сессии нет: GitHub MCP даёт `create_branch` (только `refs/heads/*`), общего
  «создать ref/тег» инструмента в наборе нет. Суб-агент (`Agent`) эту проблему не решает — у него
  тот же git-креденшел, тот же 403 (проверено разовым суб-агентом на этой самой задаче). Суб-агент
  решает другую, отдельную проблему: блокировку `Bash`-вызова классификатором авто-режима сессии —
  это отдельный слой разрешений, не git-auth, и он может пропустить то же действие, вызванное из
  свежего контекста суб-агента, когда прямой вызов в текущей сессии классификатор отклонил.
- **На проекте фактически две git-идентичности с разными правами: проксированный креденшел
  облачной сессии и личный аккаунт владельца.** Если пуш падает из облачной сессии — это не
  значит, что действие невозможно вообще. 24.08 тег `history/pre-2026-08-13`, недоступный для пуша
  облачной сессии, владелец запушил тем же именем и на тот же коммит со своей машины без проблем
  (`git log` показал tagger `pop <...>`). Рабочий путь для операций, недоступных проксированному
  креденшелу: попросить владельца выполнить push самому. Для тега отдельно есть путь через
  GitHub-веб — Releases → Draft a new release → новый тег + Target = нужная ветка/коммит → Publish
  (тег создаётся в момент публикации); не проверено на практике в этом проекте, лёгким или
  аннотированным тегом это оборачивается — конкретно в этот раз владелец запушил тег напрямую,
  минуя веб-интерфейс.
- **Проверка «этот ref уже на origin» обязана смотреть оба неймспейса.** `git ls-remote --tags
  origin` ничего не скажет о ветке с тем же именем, и наоборот — нужен и `git ls-remote --heads
  origin`. 24.08 на этом потерян лишний раунд: `roles/ORCH.md`/`BOARD.md` утверждали «вторая
  ссылка на origin», проверка одних тегов дала пусто, вывод «документы врут» оказался неверным —
  ссылка была веткой (заведена 23.08 через `create_branch`) и была на origin всё это время.
- Ниша `orch-cloud` — ровно та, под которую в `SCHEDULING.md` проектировалась роль SEC («всегда
  включённый дежурный») и которая не была построена из-за отсутствия постоянно работающей машины.
  Отдельную роль SEC заводить не нужно.

## Что ORCH НЕ делает
Не пишет предметный код/анализ/статью (это зоны A/B/C/D). Только координация, мержи, документы `coordination/`.

## Лаунч-промт ORCH
```
/loop Ты — Сессия ORCH (оркестратор) проекта THz-Unified-Optimizer. Прочитай coordination/CHARTER.md и ORCHESTRATOR.md. Каждый проход: сведи BOARD.md + sessions/*.md + ACTIVITY.md + HANDOFFS.md; кто активен — смотри claude agents --json, локов и heartbeat в проекте больше нет (CHARTER §12); разрули конфликты зон/файлов (сериализуй по времени заявки); назначь открытые HANDOFFS; следи за тегами коммитов [<ID>]+Session:; мержи готовые ветки worktree в main без форса; консолидируй [proposal] в CHARTER. Предметную работу (код/анализ/статью) НЕ делай — только координация и coordination/**, CLAUDE.md, main research/state.json. В конце — краткий отчёт владельцу: кто над чем, конфликты, что требует решения. Если остановится — повтори строку.
```

## Периодичность
ORCH удобно будить периодически (например, `/loop 15m ...`) как монитор, ИЛИ запускать вручную, когда
владелец хочет свод/мерж. Авто-продолжение ненадёжно (лимиты) → ручной повтор строки.
