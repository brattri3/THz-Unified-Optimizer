# STYLE_MANIFEST — оформление отчётов и презентаций зоны P

> Единый манифест стиля для всего, что зона P показывает владельцу. Держится в git и
> переиспользуется каждым следующим отчётом. Пример применения — `weekly/2026-08-04/REPORT.md`.
> Базис взят от прежней презентации проекта `docs/artifacts/presentation_weekly.md`
> (Marp, тёмная тема) — сохранена узнаваемость; заменена только палитра графиков (§4).

---

## 1. Формат и сборка

Исходник отчёта — **один markdown-файл с Marp-фронтматтером** (`REPORT.md`). Слайд = блок между
`---`. Никаких бинарных «мастеров» — отчёт остаётся diff-абельным и читается прямо в GitHub/IDE,
даже если его никто не собирал.

```powershell
# сборка (по желанию; в git собранные файлы не идут — см. .gitignore)
npx @marp-team/marp-cli@latest research/presentations/weekly/<дата>/REPORT.md -o out.html
npx @marp-team/marp-cli@latest research/presentations/weekly/<дата>/REPORT.md --pptx -o out.pptx
```

**Структура каталога одного отчёта:**

```
weekly/<ISO-дата>/
├── REPORT.md          # сама презентация (Marp)
├── SOURCES.md         # трассировка: число → артефакт-источник (обязателен)
└── figures/
    ├── make_figures.py  # строит графики ИЗ ЛИТЕРАЛОВ, вписанных из журнала
    └── *.png            # результат
```

## 2. Каркас недельного отчёта (проверенная последовательность слайдов)

| # | Слайд | Зачем |
|---|---|---|
| 1 | Титул: период, роль-автор, одна фраза «главное за неделю» | владелец должен понять итог, не листая |
| 2 | **Итог одной страницей** — 3–5 буллетов «что изменилось в проекте» | если дальше не читают, этого достаточно |
| 3 | Словарь недели (термины, впервые встречающиеся в отчёте) | CHARTER §11: термин определяется при первом употреблении |
| 4–N | По одному слайду на закрытый шаг: **вопрос → как проверяли → число → что это значит** | |
| N+1 | Отрицательные результаты и **отозванные числа** отдельным слайдом | их легко потерять, а они дороже положительных |
| N+2 | По ролям A/B/C/D/L: кто что сделал; «нет активности за период» — писать явно | |
| N+3 | Что открыто / что решает владелец | |
| N+4 | Что дальше | |

## 3. Регистр текста (CHARTER §11, но короче, чем в `DRAFT.md`)

- **Сначала суть, потом формализм.** Абзац начинается с фразы «что это значит», а не с формулы.
- **Термин при первом употреблении — определяется тут же**, в скобках или врезкой `> 💡`.
  Врезки `> 💡` — образовательный слой; в отчёт для владельца они ИДУТ (в статью D — нет).
- **Число без источника не пишется.** В слайде число, в `SOURCES.md` — откуда оно.
- **Неопределённость называется вслух:** «тенденция, не результат», «не проверено» ≠ «проверено и
  чисто», «отозвано». Слайд без оговорок там, где они есть в журнале, — брак.
- **Английские термины** сохраняются в оригинале (`multistart`, `bootstrap`, `AIC`), но при первом
  употреблении — с русским пояснением.
- Одна мысль — один слайд. Больше 6 буллетов на слайде = слайд надо делить.

## 4. Палитра и правила графиков

**Поверхность:** `#0f172a` (тёмный слайд), текст `#f8fafc`, вторичный текст `#94a3b8`,
сетка `#334155`. Заголовки `#38bdf8`, подзаголовки `#818cf8` — как в базовой презентации проекта.

**Категориальные слоты (в фиксированном порядке, НЕ по кругу):**

| Слот | Цвет | Роль в отчётах P |
|---|---|---|
| 1 | `#3987e5` синий | основная измеренная величина |
| 2 | `#d95926` оранжевый | сравниваемая/конкурирующая величина |
| 3 | `#199e70` бирюзовый | третья серия |
| — | `#94a3b8` серый | опорные линии, законы, эталоны (НЕ серия данных) |

Палитра прогнана валидатором навыка `dataviz` на этой поверхности
(`validate_palette.js "#3987e5,#d95926,#199e70" --mode dark --surface "#0f172a" --pairs all`):
светлотная полоса, порог цветности, разделение при дальтонизме (худшая пара ΔE 9.4),
нормальное зрение (ΔE 20.9), контраст к фону ≥3:1 — **все проверки PASS**. Менять цвета «на глаз»
нельзя: при замене — перепрогнать валидатор.

**Жёсткие правила (нарушение = график переделывается):**

1. **Никогда две оси Y.** Разномасштабные величины — два графика или общая нормировка.
2. **Цвет закреплён за сущностью, не за рангом.** Убрали серию — оставшиеся не перекрашиваются.
3. **Легенда при ≥2 сериях обязательна**; при ≤4 сериях — плюс прямые подписи, чтобы идентичность
   не держалась на одном цвете.
4. **Тонкие штрихи:** линии 2 px, маркеры ≥8 px, сетка приглушённая и позади данных.
5. **Подписи — текстовым цветом**, не цветом серии.
6. **Последовательная шкала = один тон светлый→тёмный; расходящаяся = два тона + серый центр.**
   Радуги нет никогда.
7. **Числа на графике = числа в `SOURCES.md`.** Скрипт содержит литералы с комментарием-источником
   и не имеет доступа к `data_pool/`.

**Чего в отчётах P не бывает:** круговых диаграмм долей, 3D, градиентных заливок под линией
«для красоты», подписи значения у каждой точки (только у ключевых).

## 5. Чек-лист перед сдачей отчёта

- [ ] Каждое число из отчёта есть в `SOURCES.md` с файлом-источником.
- [ ] Отозванные/непроверенные результаты помечены как таковые.
- [ ] Для каждой роли A/B/C/D/L сказано либо что сделано, либо «нет активности за период».
- [ ] Термины определены при первом употреблении.
- [ ] Графики: палитра из §4, валидатор прогнан, нет двух осей Y, есть легенда.
- [ ] Скрипт графиков не читает `data_pool/` и не импортирует модель.
- [ ] `STATE.md` зоны P обновлён, строка в `BOARD.md` обновлена, запись в `ACTIVITY.md` добавлена.
- [ ] Коммит: `[P] …` + трейлеры `Session: P` + `Reason:`; в коммит идут только пути
      `research/presentations/**` и собственные строки координации.
