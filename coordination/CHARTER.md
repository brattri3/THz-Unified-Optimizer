# CHARTER — ядро правил мультисессионной работы

> **Читать НЕ обязательно при старте.** Точка входа роли — `coordination/roles/<ID>.md`,
> универсальные гардрейлы — в `CLAUDE.md` (грузится сам). Сюда заглядывают, когда правило
> неочевидно или его собираются нарушить.
>
> Обоснования решений вынесены в `coordination/rationale/` — они в контекст не грузятся.

## 1. Идентичность

ID роли (`A`/`B`/`C`/`D`/`L`/`P`/`ORCH`) задаётся в лаунч-промте. Не задан — **спроси владельца**,
анонимно не работай.

При старте: назвать сессию (`claude -n <имя роли>`, таблица — `PROJECT.md`) или `/rename`; один раз
посмотреть `claude agents --json` — если в этом же `cwd` уже висит сессия с тем же именем в статусе
`busy`, не начинать и сообщить владельцу. Локов, таймаутов и heartbeat в проекте нет
(отменены 2026-08-15, разбор — `rationale/PARALLEL_WORK.md`).

**Три контура** (с 2026-08-23): рабочий ПК, ноутбук, облако. `claude agents` видит только текущую
машину и облачную сессию не покажет **никогда** — проверка выше действует внутри контура, не между
ними. Между контурами согласование держится на git. Облачный оркестратор носит отдельное имя
`orch-cloud`, чтобы не путать с локальным `orch`. Подробнее — `PROJECT.md`, «Три контура».

## 2. Зоны — по слою, а не по каталогу

Своя зона — в `coordination/roles/<ID>.md`; полная карта — `OWNERSHIP.md`; краткая таблица ролей —
`PROJECT.md`; история границ — `rationale/ZONES_HISTORY.md`.

Два правила, которых достаточно в 95 % случаев:

- **Общий код** (`fit_lib.py`, `model_core.py`, `model_blanco`) правит только **B**. Остальным
  read-only, правка — через `HANDOFFS.md`.
- **Не уверен, чья зона — не трогай, спроси.** Дешёвая остановка вместо дорогой ошибки.

## 3. Выход за рамки зоны — НЕ ДЕЛАЙ, перенаправь

Владелец просит то, что вне твоей специализации:

1. Не выполняй; кратко объясни, что это зона `<Y>`.
2. Запиши запрос в `HANDOFFS.md` (от кого, кому, что нужно, контекст).
3. Предложи владельцу переключиться в `<Y>` или запустить её (`LAUNCH_PROMPTS.md`).

Исключение: тривиальное чтение и справка — можно. Правки в чужой зоне — только через хэндофф.

## 4. Коммиты

- Префикс: **`[<ID>] краткое что`**.
- Трейлеры **последним абзацем, без пустой строки внутри** (иначе git их не распознаёт — проверено,
  10 коммитов из 29 за неделю 09–15.08 сломаны именно так):
  ```
  Session: <ID>
  Reason: <почему> — в ОДНУ строку, перенос ломает весь блок
  ```
  ✅ **Это проверяется автоматически** (с 2026-08-15): хук `PostToolUse`
  `.claude/hooks/check-commit-trailers.sh` после каждого `git commit` спрашивает у **самого git**,
  видит ли он трейлеры, и при отказе возвращает сессии причину с указанием, что чинить.
  Правило переведено из разряда «надо помнить» в разряд «проверяется» — ровно то, чему научил
  аудит: правила, встроенные в действие, держатся сами.
- Коммить **только свои пути**, `git add -A` вслепую — нет.
- `git push` — **только с прямого разрешения владельца**. Форс и переписывание истории — никогда.
- Конфликт общего файла на `main` → не форсить, звать ORCH.
- В координационных документах не ссылаться на хеши: ссылка по дате + файлу.

## 5. Изоляция (git)

Общий каталог на `main` — для работы с живыми общими данными. **Worktree + ветка** рекомендуется
тем, кто активно правит общий код (B) или изолирован (C):
`git worktree add ../TUO-<ID> session/<ID>`. Мержит ORCH.

## 6. Протокол работы

**Холодный старт — один раз за чат** (и заново после `/clear`, `/compact`): `CLAUDE.md` грузится
сам, прочитать `coordination/roles/<ID>.md`. Всё.

**Пульс — на каждом атомарном шаге:**

1. Свой рабочий `state.json` → первая не-`done` задача.
2. Выполнить **один** атомарный шаг.
3. Числа → `research/logs/RESEARCH_LOG.md` с тегом `[<ID>]`. Значимое изменение → `ACTIVITY.md`.
4. Обновить `state.json`; если появилась находка или решение — свой `roles/<ID>.md`.
5. Гардрейлы `research/RESEARCH_PLAN.md §6` действуют всегда.

## 7. Разрешение конфликтов

- **Роль давно не работает** → ORCH переназначает задачи. Признак: её нет в `claude agents` **и**
  нет коммитов за разумный срок. Файлы роли ничего не «держат».
- **Два чата одной роли** → видно в `claude agents`. Второй не начинает. Между разными машинами
  этого не видит ни один механизм — согласование через git.
- **Пересечение зон** → арбитр ORCH; без него решает владелец.
- **Общий файл нужен двум** → кто первый заявил в `ACTIVITY.md`, второй ждёт.

## 8. Фоновые работники (subagent)

Запустил работника, тронувшего репозиторий → **одна** запись в `HANDOFFS.md`: задание как выдано /
что вернулось (ветка и коммит, не «сделал») / вердикт / промах в самом задании, если был.
Транскрипты не хранятся. Зачем каждый пункт — `rationale/BACKGROUND_WORKERS.md`.

**Находка, живущая только в переписке с работником, считается потерянной** — её место в коде,
коммите или записи.

**Граница: субагент — не сессия роли** (уточнено 2026-08-23). У субагента своё контекстное окно,
он стартует с нуля (истории вызвавшей сессии не видит), вызов не переживает, транскрипт не
хранится, `claude agents` его не показывает, вложенность ограничена. Отсюда:

- **Годится** для ограниченной проверяемой задачи с письменным результатом: аудит, замер, поиск,
  сверка, разбор. Задание должно быть самодостаточным — субагент не «дочитает контекст».
- **Не годится** для ведения зоны. Зона требует памяти между заходами и ответственности за
  состояние; ни того, ни другого у субагента нет. Роль ведёт сессия, а не работник.
- Запускать субагентов может любая сессия; для облачного `orch-cloud` это штатная функция
  (`ORCHESTRATOR.md`), но правило записи в `HANDOFFS.md` для него то же самое.

## 9. Стиль общения с владельцем

Владелец — постановщик задачи, но **не математик и не физик** в тех разделах, где идёт работа
(поляризационная оптика, матрицы Джонса, статистика нелинейных фитов, идентифицируемость, UQ).
Поэтому все сессии обязаны:

- **Профессиональный регистр** — рассуждать как физик-теоретик, методы называть по именам.
- **Обучать, а не отчитываться** — определять термин при первом употреблении, давать физическую
  интуицию до формализма, называть пререквизиты.
- **Слоистая подача** — сначала суть в двух фразах, затем строгая формулировка, затем разбор.
  Не вываливать стену формул.

## 10. Оркестратор и доработка

ORCH — сессия-контролёр: сводит роли, мержит ветки, разруливает конфликты, держит `coordination/**`
и `CLAUDE.md` в актуальности. Спецификация — `ORCHESTRATOR.md`.

Предложения по парадигме → `ACTIVITY.md` с тегом `[proposal]`; консолидирует ORCH.

**Отдельная обязанность ORCH:** следить, чтобы отменённое не отрастало. Новое правило, отвечающее
на вопрос «кто сейчас работает», заведомо лишнее — ответ даёт `claude agents`.
